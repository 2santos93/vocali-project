# auth

The Cognito user pool and the single app client the Nuxt BFF authenticates
against.

## What it decides

**Email is the username, and verifying it is mandatory.** The pool
auto-verifies `email`, so an account cannot sign in until the code sent at
sign-up has been entered. Account recovery goes to that same verified address
and nowhere else — there is no SMS mechanism, which is the usual way an
account is taken over by porting a number.

**The client is confidential.** It has a secret, so every call carries a
`SECRET_HASH` and a leaked client id alone is not enough to attack the pool.
It can hold a secret because it is only ever used from the Nitro server
routes; nothing here is reachable from browser JavaScript. The tokens then
live in `httpOnly` cookies that the same server sets.

**Token lifetimes are stated, not defaulted.** Cognito's defaults are one
hour for the access and identity tokens and **thirty days** for the refresh
token. The defaults here are fifteen minutes and eight hours.

| Token   | Default | Here    | Why                                                                                                     |
| ------- | ------- | ------- | ------------------------------------------------------------------------------------------------------- |
| Access  | 60 min  | 15 min  | An access token cannot be revoked. Its lifetime is the window an attacker keeps after a theft.          |
| ID      | 60 min  | 15 min  | Matched to the access token so a session has one expiry rather than two.                                |
| Refresh | 30 days | 8 hours | The refresh token is the session. A working day is long enough for a shift and short enough to contain. |

Token revocation is enabled, which is what makes sign-out real: `GlobalSignOut`
invalidates the refresh token instead of merely clearing the cookies.

**User enumeration is off.** `prevent_user_existence_errors` collapses "no
such user" and "wrong password" into one answer. For a medical service the
list of people who hold an account is itself sensitive.

## What it does not do

- No hosted UI, no OAuth flows, no user pool domain. Sign-in is our own form
  posting to our own server, which removes the redirect allow-lists and the
  callback handling.
- No MFA. Stated rather than omitted: it is not in scope, and enabling it
  without an enrolment path would lock users out at first sign-in. A pool can
  move from `OFF` to `OPTIONAL` later without being recreated.
- No advanced security features. They require the Plus tier and are priced
  per monthly active user.
- Cognito's built-in email sender, which has a low daily cap. A tenant with
  real users would point `email_configuration` at SES.

## The client secret

`user_pool_client_secret` is generated by AWS, so it is written to the state
file whether or not it is exposed as an output. That is the reason the state
bucket has a customer-managed key and no public path to it. Read the secret
out with `terraform output -raw`, put it where the BFF reads it at runtime,
and treat anyone with `s3:GetObject` on the state bucket as holding it too.
